# MG-01 — Target Architecture

## Architecture Overview
Microservice-based (`target.architecture.type`). A React single-page app calls one REST microservice, `TransactionTypeService` (ASP.NET Core Web API, .NET 9), through the API gateway path `/api`. The service owns the `transaction_type` table in PostgreSQL database `carddemo`. Requests are stateless; the UI holds filter and paging state (`target.state.management`).

## Component & Layer Definitions
| Component | Responsibility | Technology (Config.md) |
|---|---|---|
| UI app | Screens S1–S3, client validation, confirmation dialogs, client-held paging state | React + Tailwind CSS, Vite dev server :5173 |
| API gateway / dev proxy | Routes `/api/*` to the service; TLS termination in shared environments | API gateway (`target.api.layer`); Vite proxy in local dev |
| TransactionTypeService – Controllers | HTTP contract E1–E6, auth policies, ProblemDetails | ASP.NET Core Web API, C# (.NET 9), :5000 |
| – Services | Business rules R1–R25, validation, error mapping | C# |
| – Repositories | Keyset queries, CRUD, transactions | EF Core 9 + `Npgsql.EntityFrameworkCore.PostgreSQL` |
| Database | `transaction_type` (PK `tr_type`) | PostgreSQL 15 (`carddemo`) |
| Identity provider | Issues JWTs (role `carddemo.admin`) | OAuth 2.0 provider at `http://localhost:8081` (not running locally; dev bypass) |

No cache (Redis) or messaging (Kafka/RabbitMQ) is needed for MG-01.

## Interaction / Data Flow
```
Browser (S1/S2/S3)
  │  HTTPS, Authorization: Bearer <JWT>
  ▼
/api  (gateway or Vite proxy)
  ▼
TransactionTypesController ──► TransactionTypeService ──► TransactionTypeRepository ──► CardDemoDbContext ──► PostgreSQL
        ▲                              │ validation, rules, error mapping
        └──── 200/201/204 JSON or ProblemDetails ◄──────────────────────────────────────────────┘
```
1. List: S1 → `GET /api/v1/transaction-types?…` → validate filters → keyset SELECT (+1 look-ahead) → page JSON.
2. Inline update / Save changes: confirm dialog → `PUT …/{code}` → validate → BEGIN; SELECT … FOR UPDATE; compare; UPDATE; COMMIT → 200.
3. Create: confirm → `POST …` → validate/normalise → INSERT (PK conflict → 409) → 201.
4. Delete: confirm → `DELETE …/{code}` → DELETE (FK violation → 409) → 204 → S1 reloads page 1.

## Data Architecture
- `transaction_type (tr_type CHAR(2) PK, tr_description VARCHAR(50) NOT NULL)`, unique index `xtran_type`; seeded with 7 rows (Phase 5).
- Referenced (future) by `transaction_type_category.trc_type_code` with `ON DELETE RESTRICT` — owned by a later group.
- Schema is owned by `Artefacts/DDL/MG-01-TransactionTypeMaintenance-schema.sql`; the service does not run migrations.

## Security & Compliance Architecture
- **OAuth 2.0 / JWT:** validated in the service (JwtBearer, JWKS from the identity provider); policy requires `carddemo.admin`. Dev bypass handler only in Development.
- **TLS 1.3:** at the gateway or Kestrel outside local dev.
- **OWASP:** validation and parameterised SQL in the service; security headers; rate limiting; CORS restricted to the UI origin in dev.
- **GDPR:** no personal data; audit log entries carry the admin `sub` only.
- **Accessibility:** UI responsibility, fed by machine-readable error codes from the service.

## Deployment/Topology (logical only)
