# MG-02 — Target Architecture (Sign-on and Navigation Shell)

## Architecture Overview
The architecture is microservice-based (config/Config.md). MG-02 adds **SignOnService**, an ASP.NET Core 9 microservice that owns `usrsec`. It authenticates users, issues RS256 JWT access tokens and publishes the OIDC discovery and JWKS documents. It also serves the role menus.

A single **CardDemo shell SPA** (React/Vite/Tailwind) hosts the sign-in page and both menus, and mounts already-migrated group screens: MG-01 transaction types now, later groups as they arrive. Each group's API, such as MG-01 TransactionTypeService, validates the shell's token through its existing `Auth:Authority`.

## Component & Layer Definitions
| Component | Responsibility | Technology |
|---|---|---|
| Shell SPA | Sign-in, menus, route guards, in-memory session, hosting of MG-01 screens | React 18, Vite 6, Tailwind 3, React Router 6 |
| SignOnService API | `/api/v1/auth/sign-in`, `/api/v1/menus/{main,admin}`, `/.well-known/*`, `/health` | ASP.NET Core 9 minimal API |
| Token issuer | RS256 JWT signing; publishes the JWKS | Microsoft.IdentityModel.JsonWebTokens |
| Data access | Read-only lookup in `usrsec` | EF Core 9 + Npgsql |
| TransactionTypeService (MG-01) | Unchanged code. Configured to trust SignOnService. | ASP.NET Core 9 |
| Database | `usrsec` (MG-02), `transaction_type` (MG-01) | PostgreSQL 15 |

## Interaction / Data Flow
```
Sign in:   SPA /signin --POST /api/v1/auth/sign-in--> SignOnService --SELECT usrsec by id--> PostgreSQL
           <-- 200 {accessToken, user} -- (token kept in memory) --> route by userType (/admin | /menu)
Menu:      SPA /admin --GET /api/v1/menus/admin (Bearer)--> SignOnService (role check) --> MenuCatalog --> options[]
Function:  tile "Transaction Type List/Update" --> /transaction-types --GET /api/v1/transaction-types (Bearer)-->
           TransactionTypeService --(JWKS from SignOnService, cached)--> validate --> PostgreSQL transaction_type
```

## Data Architecture
- `usrsec` (read-only for SignOnService): key `sec_usr_id`. Holds identity, display name, plain-text password (demo) and user type.
- Menu options are static configuration cited to COMEN02Y and COADM02Y. They are not stored in the database.

## Security & Compliance Architecture
- OAuth 2.0 bearer JWT: RS256, `aud=carddemo-api`, `role` and `scope` claims, 15-minute expiry. Every API validates the token. The SPA holds the token in memory only.
- TLS 1.3 on all APIs outside Development (MG-01 pattern), and `StartupGuards` for signing key, authority and plain-text passwords.
- OWASP controls:
  - sign-in rate limit
  - constant-time password comparison
  - no password logging
  - ProblemDetails responses with no stack traces
  - CORS allow-list
  - security headers
- Personal data (names) is shown only to the signed-in user, and audit events contain no passwords.
- Accessibility: WCAG 2.2 AA in the SPA.

## Deployment/Topology (logical only)
`Browser → Shell SPA (5173, proxies /api) → { SignOnService :5001 , TransactionTypeService :5000 } → PostgreSQL :5433`.

## Open Architecture Decisions
1. Plain-text passwords (user decision) are demo-only. Production needs hashing or an external IdP.
2. Showing distinct messages for an unknown user and a wrong password exposes which user IDs exist. This is kept for parity.
3. One shell SPA versus micro-frontends. One SPA was chosen for simplicity.
4. Whether SignOnService should become the long-term identity provider, or be replaced by the enterprise IdP once its realm and roles are known.
